GigRadar

Why I built a personal London live-music radar, how it solves grassroots gig discovery, and an experiment in agent-orchestrated full-stack engineering.

I love London's grassroots live music scene: small pub backrooms, community spaces, and independent venues across Hackney, Brixton, Camden, Peckham, and Dalston. But keeping track of what was happening on any given night was exhausting. Commercial ticketing apps (DICE, Ticketmaster, Songkick, RA) are heavily geared towards promoted headliners, festival packages, and ticket markups. They routinely miss the small £5-£10 DIY gigs, pub jazz sessions, and emerging indie bands that make London's music culture special.

The grassroots scene is fragmented: some venues maintain basic HTML calendar tables, others use ICS feeds, and many post only a graphic flyer to Instagram. By the time I found out about an intimate gig through word of mouth, tickets were either already sold out or the date had passed. I built GigRadar to solve my own problem: a clean, consolidated live radar that scrapes independent venue calendars directly, extracts structured show dates from messy poster images using local vision models, and tracks ticket status changes so I never miss an intimate gig.

It was also a great opportunity to get hands-on with a modern full-stack toolchain. I wanted to build a complete system from scratch: using AI coding agents for research and refactoring, running local multimodal models (Ollama) to parse flyers without API bills, using PostgreSQL with pgvector for deduplication, and deploying a fast SvelteKit client to Cloudflare Pages.

Multi-Source Ingestion & Adapters

Grassroots venues don't have standardized APIs. I wrote custom adapters and feed parsers that convert raw venue web pages, ICS calendars, and poster uploads into immutable RawObservation records, preserving source DOM snapshots for debugging and auditing.

Semantic Deduplication with pgvector

When the same gig is listed on a venue site and a promoter flyer with slight spelling variations, GigRadar uses deterministic slug matching with a fallback to pgvector cosine similarity. Borderline matches are routed to a quick review queue.

Edge Client & Clean Separation

To keep the public demo fast and secure without exposing internal database credentials or incurring server costs, the frontend runs as an edge-rendered SvelteKit app on Cloudflare Pages using Web Crypto HMAC session signing.

Architectural Decisions

Engineering Decisions & What I Learned

Data Ingestion

Direct Grassroots Scraping vs Mainstream Ticketing APIs

Decision

Build custom DOM scrapers and feed adapters for individual grassroots venues rather than relying on DICE, Ticketmaster, or Songkick APIs.

Why

Mainstream APIs only list events with formal commercial ticketing partnerships. Scraping grassroots calendars and reading flyers directly captures the small £5-£10 pub backroom gigs and community nights that aggregators completely ignore.

Alternatives Considered

Commercial aggregator APIs (DICE, Ticketmaster Discovery, Resident Advisor GraphQL).

Trade-offs & Rationale

Venue web markup changes over time. I learned to build resilient scraping abstractions behind a common BaseAdapter interface with fallback fixtures and automated DOM snapshot tests.

Database & Vectors

PostgreSQL + pgvector vs Dedicated Vector Databases

Decision

Use a single PostgreSQL instance with the pgvector extension for both relational event metadata and semantic vector search.

Why

Keeping event details, venue metadata, ticket status history, and vector embeddings in one database gives full ACID transactional consistency. It completely eliminated the dual-write sync bugs and extra operational overhead of running a dedicated vector DB (like Pinecone or Qdrant).

Alternatives Considered

Pinecone, Qdrant, ChromaDB, or PostgreSQL full-text search (tsvector).

Trade-offs & Rationale

Standalone vector DBs scale higher for multi-million vector datasets, but for tens of thousands of London events, PostgreSQL HNSW indexing delivered sub-millisecond vector queries with zero infrastructure bloat.

AI Strategy

Local Ollama Models vs Cloud AI APIs

Decision

Run all multimodal flyer OCR (qwen3-vl) and text embeddings (nomic-embed-text) locally via Ollama rather than using paid cloud vision APIs.

Why

Cloud AI APIs introduce recurring per-image bills, network latency, and vendor lock-in. Running lightweight models locally gives me a private sandbox where I can parse hundreds of event posters offline without worrying about API limits or costs.

Alternatives Considered

OpenAI GPT-4o-mini vision API, Anthropic Claude 3.5 Sonnet, Google Gemini 1.5 Flash.

Trade-offs & Rationale

Local vision inference takes 2-3 seconds on my machine compared to sub-second cloud APIs. Because flyer processing is an asynchronous background task, zero cost and offline reliability matter much more than instant responses.

Backend Architecture

FastAPI with Pydantic v2 Contract Boundaries

Decision

Standardize backend services on FastAPI with Pydantic v2 schemas for strict boundary validation and native asynchronous concurrency.

Why

Polling multiple venue endpoints concurrently requires an async-native runtime (ASGI). Pydantic v2's Rust core delivers ultra-fast schema serialization and guarantees strict type enforcement when parsing semi-structured JSON outputs from local AI extractors.

Alternatives Considered

Django REST Framework (synchronous, heavy batteries), Flask (lacks native async and type validation).

Trade-offs & Rationale

Requires configuring SQLAlchemy async sessions and Alembic migrations manually, but gave complete granular control over database connection pools and async execution.

Deployment & Edge

Edge SvelteKit Deployment & Cloudflare Pages

Decision

Deploy the frontend showcase as an edge SvelteKit application on Cloudflare Pages, isolated from the stateful database, using Web Crypto API HMAC-SHA256 signed session tokens.

Why

Eliminates serverless cold starts, provides global edge distribution (<50ms response), and prevents surprise cloud infrastructure bills. The deterministic sample dataset ensures 100% demo reliability without exposing internal database credentials.

Alternatives Considered

Vercel, AWS Amplify, static export with hardcoded string cookie auth.

Trade-offs & Rationale

Requires isolating write paths and using mock fixtures for the public demo. Web Crypto HMAC verification provides edge-native security with constant-time signature comparison without requiring Node.js runtime bindings.

Agent Tooling & Workflow

Agent Orchestration & ADR-Driven Engineering

Decision

Develop the entire project using structured AI coding agents, driven by explicit Architectural Decision Records (ADRs) and strict type boundaries.

Why

Rather than typing vague prompts into a chatbot, I used AI coding agents with clear roles: delegating research, schema design, and test generation while enforcing strict repository guidelines and automated quality checks.

Alternatives Considered

Manual unstructured coding, single-prompt AI generation.

Trade-offs & Rationale

Writing ADRs and types upfront took a bit of initial effort, but it kept the AI agents on track, maintained consistent code style, and made polyglot refactoring across Python and TypeScript smooth and predictable.

Developer Experience & Tooling

Development Process & Tooling Stack

Agent Orchestration & AI Workflows

I structured development around AI coding agents with defined scopes: using subagents for codebase exploration, writing explicit ADR specs before implementing features, and running automated test suites before merging changes.

# Spec-driven development & verification
docs/adr/003-ollama-vision.md

Python Toolchain Authority (uv)

I enforced a strict single-toolchain boundary: uv is the sole authority for Python 3.12+ virtual environment creation (.venv), lockfile resolution, and script execution. It resolved packages in milliseconds and eliminated broken virtualenv paths.

uv sync --all-extras
uv run pytest tests/ -v

Polyglot Task Runner (Justfile)

All developer workflows are standardized behind declarative Justfile recipes. Instead of juggling different CLI flags across Python, Node, and Podman, one command starts the stack or runs the whole test suite.

just dev: Start backend & edge frontend
just review-fast: Run all lint, type & test gates

Rootless Containers (Podman Compose)

Local infrastructure services (PostgreSQL 16, pgvector, Ollama model runner) are orchestrated using Podman Compose in rootless mode, keeping my local development environment isolated without requiring a privileged Docker daemon.

just up: Launch PostgreSQL + pgvector container
just down: Cleanly teardown background services

Zero-Drift Type Gates & Linters

Enforced strict quality gates combining Pyright strict static type checking, Ruff for sub-millisecond linting and formatting, and SvelteKit check for template type safety across the frontend.

uv run ruff check . && uv run pyright
npm --prefix apps/demo run check

Automated Preview Smoke Tests

The CI pipeline executes an automated Node.js smoke testing harness against live Cloudflare Pages preview builds, validating 18 critical assertions across public routes, HMAC auth redirects, guest mode, logout, and self-hosted fonts.
