GigRadar

A way to keep up with small London venues and find gigs before I’ve missed them.

Open demo ↗All projects →

Why I’m building it

I kept finding out about gigs after they had happened or sold out. Following individual venues meant checking several sites and hoping I hadn’t missed an announcement.

GigRadar brings that information together. The aim is simple: browse events, find venues on a map and follow the places and artists I care about.

The data work

The difficult part is keeping event information consistent across sources. Dates change, the same gig appears in more than one place, and a missing listing doesn’t necessarily mean an event is cancelled.

I’m working on source ingestion, event identity and retaining the evidence behind each update. A ticket-status label should be traceable to a source.

What exists now

Public demo
A static event snapshot for trying the interface without exposing the development system or running collection jobs online.
Development app
Event, venue and artist records, alongside map, saved and favourites views.
Data collection
Manual local pulls through configured source adapters, followed by normalisation, identity checks and snapshot export.
Still in progress
Broader source coverage, evidence-based urgency labels and interface polish. Scheduled collection comes later.

One useful decision

I separated the public demo from the development application. Collection and validation can change while I work out which sources are reliable; the public site receives a checked snapshot and stays cheap and safe to host.

sources → normalise → retain evidence → export snapshot → public demo

What I’ve learned

The interface is the easy part. The real work is deciding when two listings describe the same event, recording where each fact came from and handling a source disappearing without silently calling the event cancelled.

Flyer extraction and more detailed event signals are areas I’m exploring. They are not promises about what the demo can currently do.
