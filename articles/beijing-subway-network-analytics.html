Beijing Subway: Spatial Data Engineering and Network Resilience

Author: George Willis
Keywords: Transit data engineering, OpenStreetMap, timetable synthesis, spatial data, network analysis, resilience

Overview

TransitFlow is an open spatial data and simulation project built around the Beijing Subway. It combines OpenStreetMap data, published transport information, spatial transformations and a synthetic timetable to build a network model for simulation and resilience analysis.

The difficult part was turning inconsistent public data into a single network that the application could use consistently. The workflow covers data extraction, station matching, coordinate handling, timetable generation and network analysis.

The current model contains 25 operational corridors, 414 station complexes and 493 inter-station edges, with 8,603 simulated vehicle runs across a 24-hour service day.

The figures below are outputs from the TransitFlow model and should be read alongside its assumptions and limitations.

1. Building the network

Transit data rarely arrives in one clean package. OpenStreetMap provides detailed geometry, while timetable and operating information may be published separately and at a different level of detail.

TransitFlow focuses on three practical problems:

  1. Building the network from OpenStreetMap station and track data.
  2. Using a common coordinate system so distances and geometry can be calculated in metres.
  3. Creating a usable timetable when a complete public GTFS feed is not available.

2. Data and spatial processing

OpenStreetMap

OpenStreetMap provides the underlying station and track geometry. The Beijing extraction used for the model contains 13,902 railway way segments and 547 raw station nodes before cleaning and consolidation.

Station records are matched and clustered so that multiple platforms belonging to the same physical interchange can be represented by a single station complex where appropriate. The final graph contains 414 station vertices and 493 inter-station edges.

Coordinate systems

OpenStreetMap coordinates are provided in WGS84 (EPSG:4326). Distance calculations are performed after reprojection to UTM Zone 50N (EPSG:32650), giving metric coordinates for local geometry calculations.

Where Chinese mapping coordinates such as GCJ-02 or BD-09 are involved, the project accounts for the differences rather than treating them as interchangeable.

Network representation

TransitFlow uses an L-space representation for its main network graph. Stations are vertices and consecutive stops on a line form edges. This makes it straightforward to attach geometry, distance and simulated running time to each edge.

3. Timetable reconstruction

A complete public GTFS feed was not available for the model, so TransitFlow generates a synthetic 24-hour timetable from published headway ranges and operating assumptions.

Headways vary through the day. For each line, trains are generated in both directions and station arrival and departure times are calculated from inter-station distance, an assumed operating-speed profile, acceleration and braking parameters, and station dwell times.

This produces 8,603 simulated vehicle runs over a 24-hour day. The timetable is intended to give the simulation a plausible operating pattern, not to reproduce the real Beijing Subway timetable exactly.

4. Smooth vehicle movement

The browser simulation needs trains to move smoothly along curved track geometry. TransitFlow therefore evaluates positions along the track using arc-length parameterisation and cubic Hermite interpolation, with tangent estimates derived from neighbouring geometry points.

This keeps the animation continuous through bends and between track points. It is a simulation and visualisation technique, not a claim about the exact speed profile of real trains.

5. Model checks

Spatial checks

A sample of station locations was compared with reference imagery and mapping data. The model reports a mean station error of 6.42 metres and a maximum of 11.8 metres for the sample used in the project.

Dispatch volume

The generated timetable contains 8,603 runs. The project compares this with an external daily dispatch figure of approximately 8,750 runs, a difference of 1.68%.

This is a useful scale check, but it does not show that the synthetic schedule matches the real service pattern.

Travel times

The model also compares simulated journey times with values from the Beijing Subway journey planner. For the sample used by the project:

T_simulated = 0.991 × T_official + 0.42 min R² = 0.984 | RMSE = 1.42 min

The sampled routes therefore produced similar journey times. These results should be treated as a check on the model, not as proof that the complete operating system has been reproduced.

6. Network resilience

With the network in place, graph metrics can be used to identify stations whose removal has a large effect on connectivity and journey times.

TransitFlow uses measures including betweenness centrality and global network efficiency. A station with high betweenness matters because many shortest paths pass through it. Removing it can force journeys onto longer routes.

Line 10 and orbital connectivity

Line 10 is interesting because its orbital route provides an alternative to travelling through central Beijing. In the model, reducing access to the orbital route pushes some cross-city journeys towards central interchanges.

The model estimates that Line 10 is involved in 38.2% of cross-city origin-destination journeys in the simulated network. This is a model result, not a direct observation of passenger movements.

Station disruption

The model also tests individual station failures. Xizhimen produces the largest disruption in the current network configuration, with an estimated 8.4-minute increase in average journey time when removed.

The useful result is the relative vulnerability of the network. It is not a prediction of exactly what a real closure would do on a particular day.

7. Limitations

Synthetic timetable. The timetable is generated from published headway assumptions rather than a complete operational feed. Real services vary with disruption, short turns, engineering work and day type.

Station geometry. Large underground interchanges are simplified to a station-level graph. Walking routes inside stations are represented by estimated transfer costs rather than a full pedestrian network.

Crowding. Transfer and dwell penalties are represented by fixed parameters. The simulation does not model individual passengers moving through crowded platforms and concourses.

Calibration. The comparison figures are checks against selected external references. They are not a formal validation of the entire operating system.

8. What the project shows

The main lesson from TransitFlow is that the difficult part of a transport simulation is often the data work around the model.

Building the network meant deciding how to merge station records, handle coordinates, represent interchanges and create a timetable from incomplete public information. Once those pieces were in place, standard graph methods could be used to explore resilience and alternative routes.

It also shows why model assumptions need to stay visible. A polished simulation can look more precise than its inputs justify if synthetic data is presented as observed operational data.

For me, that is the useful part of TransitFlow: taking messy public geospatial data and turning it into something that can be explored, tested and extended.
